# FileFlow

Asynchronous file processing lab: FastAPI, PostgreSQL, MinIO, Kafka.
A learning project for distributed-systems patterns (transactional outbox,
idempotent consumers, retries/DLQ, leases, graceful shutdown).
The phase plan is in [docs/PLAN.md](docs/PLAN.md).

> Status: Phase 11 — large files: end-to-end streaming upload, size limits, measured memory/throughput.

## Run (hybrid dev)

Infrastructure runs in Docker, Python runs on the host:

```bash
docker compose up -d --wait          # postgres, minio (+bucket), kafka (+topic)
uv sync
uv run alembic upgrade head          # apply DB migrations
uv run uvicorn app.api.main:app --reload
uv run python -m app.outbox          # another terminal: relays outbox -> Kafka
uv run python -m app.worker          # another terminal: Kafka consumer
uv run python -m app.recovery        # another terminal: requeues due retries
open http://localhost:8000           # UI
curl localhost:8000/health
```

Upload and inspect a file:

```bash
curl -F "file=@README.md" localhost:8000/files      # multipart (HTML-form style)
curl -X POST -T big.txt -H 'Content-Type: text/plain' \
     'localhost:8000/files/stream?filename=big.txt'  # raw body, streamed end to end
curl localhost:8000/files/<file_id>
curl localhost:8000/tasks/<task_id>                 # COMPLETED + result once a worker ran
```

Everything in containers instead (a one-shot `migrate` service runs first):

```bash
docker compose --profile app up -d --build
docker compose --profile app up -d --scale worker=3   # more workers (useful only up to the partition count)
```

## Messaging: transactional outbox + Kafka

The API never talks to Kafka. An upload's final transaction writes the file
status, the `PENDING` task **and** a `TaskQueuedEvent` row in `outbox_events`
— all or nothing. The outbox publisher (`python -m app.outbox`) claims
`PENDING` rows (`FOR UPDATE SKIP LOCKED`), sends them to topic
`file-processing` (key = `task_id`), and marks the acked ones `PUBLISHED` in
the same transaction. Kafka down -> rows wait (`attempts`, `last_error`), no
loss. Publisher crash after sending but before commit -> the row is sent again:
a duplicate with the same `event_id` (`experiments/phase06_publisher_crash.sh`).
The outbox row id *is* the `event_id`.

Event: `{event_id, task_id, file_id, attempt}`. Workers form the consumer group `fileflow-workers`; each
partition is read by exactly one worker, so partitions cap parallelism.

The topic is created explicitly by `kafka-init` (auto-creation is off); the API
and workers refuse to start if it is missing, instead of waiting silently.

Delivery is **at-least-once**: auto-commit is off and a worker commits a
message's offset only after the task outcome is stored. Per message:
processed -> commit; invalid / task not `PENDING` -> skip (commit);
infrastructure error -> no commit, seek back, retry after a pause.

**Idempotent processing.** Duplicates are expected (Kafka redelivery, outbox
re-publish), so `ProcessingService.process()` returns an explicit outcome:
`processed`, `duplicate` (task already finished), `in_progress` (another worker
holds it) or `stale` (we lost the task mid-way; our result is discarded). Three
guards: the state machine (only `PENDING` can be claimed), a **fencing token**
(`complete`/`fail` require the `attempt` returned by `start`, so a previous
owner can never overwrite the current one), and `UNIQUE(task_results.task_id)`
as the last line of defense. No inbox table: `task_id` is the natural
idempotency key. See `experiments/phase07_duplicate_delivery.sh`.

**Retries.** Failures are classified (`app/retry.py`): permanent — corrupted
object (checksum), binary file, missing object/file row — go straight to
`FAILED`; everything else (MinIO/DB/network trouble, unknown errors) is
retryable. A retryable failure with attempts left moves the task to `RETRY`
with `next_attempt_at = now() + min(max, base * factor^(n-1)) ± jitter`
(defaults ~5s, 25s, 2min, 10min; 5 attempts). The **recovery** process
(`python -m app.recovery`) finds due `RETRY` tasks (`FOR UPDATE SKIP LOCKED`)
and, in one transaction, moves them to `PENDING` and writes a new
`TaskQueuedEvent` to the outbox. No sleeping in the worker, no retry topics.
See `experiments/phase08_retries.sh`.

**Dead letter queue** (`file-processing-dlq`). Every `DeadLetter` is
self-contained (`kind`, `task_id`, `file_id`, `attempt`, `error`, `failed_at`,
and for rejected messages `source` + `raw_value`). Two paths, one rule — the
decision is committed only together with its dead letter:
- a task ending `FAILED` (permanent error or budget exhausted): the dead letter
  is an outbox row written in the **same transaction** as `FAILED`;
- a message the worker rejects (invalid JSON, unknown task): the worker
  publishes the dead letter **before** committing the offset; if the DLQ is
  unreachable it does not commit and retries.

Operational recovery, after fixing the cause:

```bash
uv run python -m app.dlq list              # recent dead letters
uv run python -m app.dlq redrive TASK_ID   # FAILED -> PENDING, +task_max_attempts budget
```

Redrive never resets `attempt` (it is the fencing token); it raises the task's
`max_attempts`. `FAILED -> PENDING` is a manual transition: for the pipeline
`FAILED` stays terminal. The DLQ is a log, so redriven dead letters remain.
See `experiments/phase09_dlq.sh`.

**Large files.** Two upload paths:
`POST /files` (multipart; Starlette spools the whole body to a temp file
before our code runs) and `POST /files/stream?filename=` (raw body read from
the socket with `request.stream()` and piped through hashing into the S3
multipart upload — nothing on disk, at most one 8 MiB part in memory, and TCP
backpressure reaches the client). Both enforce `max_upload_bytes` while
streaming (413; `Content-Length` checked up front), and any error while
receiving the body (too large, client gone, MinIO down) aborts the multipart
upload and marks the file `FAILED`. Measured with a 1 GiB text file
(`uv run python -m experiments.phase11_large_files`, laptop, compose):

| upload    | time   | API cgroup memory | API process RSS | temp disk | `/health/live` p99 / max |
|-----------|--------|-------------------|-----------------|-----------|--------------------------|
| multipart | 33–43s | ~1.2 GiB          | 180 MiB         | 1 GiB     | 14 / 31 ms               |
| stream    | 21–27s | ~150 MiB          | 156 MiB         | 0         | 12 / 20 ms               |

The multipart "memory" is the kernel page cache of the spooled file, charged to
the container's cgroup (relevant for container memory limits), not the
process. Hashing in the event loop adds ~10 ms at p99 (idle: 6 ms) — measured,
not worth moving to a thread. Processing 1 GiB in the worker: ~6.5 s with a
flat ~90 MiB. Reading the whole file into memory before analysis peaks at
**~9.9 GiB RSS** for a 1 GiB file (`bytes.split()` materializes every word);
streaming stays at ~45 MiB, and 64 KiB chunks were the fastest.

Known flaws, accepted:
- **Stuck tasks**: a worker killed mid-task leaves it in `PROCESSING`; the
  redelivered event is answered `in_progress`
  (`experiments/phase05_kill_consumer.sh`). Leases + recovery are a documented
  perspective, not implemented (`docs/PLAN.md`).

## Task state machine

```text
PENDING ──> PROCESSING ──> COMPLETED
   ▲                 ├───> FAILED   (permanent error, or attempts exhausted)
   │                 └───> RETRY ─┐ (retryable error, attempts left)
   └──────────────────────────────┘ (recovery, once next_attempt_at is due)
```

A file becomes `UPLOADED` and gets its `PENDING` task in one transaction.
Transitions are guarded UPDATEs (`WHERE status IN <allowed sources>`), so
concurrent claims cannot both win — see `experiments/phase03_claim_race.py`.
