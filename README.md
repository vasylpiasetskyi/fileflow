# FileFlow

Asynchronous file processing lab: FastAPI, PostgreSQL, MinIO, Kafka.
A learning project for distributed-systems patterns (transactional outbox,
idempotent consumers, retries/DLQ, leases, graceful shutdown).
The phase plan is in [docs/PLAN.md](docs/PLAN.md).

> Status: Phase 05 — Kafka: API publishes events, workers consume them in a consumer group.

## Run (hybrid dev)

Infrastructure runs in Docker, Python runs on the host:

```bash
docker compose up -d --wait          # postgres, minio (+bucket), kafka (+topic)
uv sync
uv run alembic upgrade head          # apply DB migrations
uv run uvicorn app.api.main:app --reload
uv run python -m app.worker          # in another terminal: Kafka consumer
open http://localhost:8000           # UI
curl localhost:8000/health
```

Upload and inspect a file:

```bash
curl -F "file=@README.md" localhost:8000/files      # -> 201: {file: UPLOADED, task: PENDING}
curl localhost:8000/files/<file_id>
curl localhost:8000/tasks/<task_id>                 # COMPLETED + result once a worker ran
```

Everything in containers instead (a one-shot `migrate` service runs first):

```bash
docker compose --profile app up -d --build
docker compose --profile app up -d --scale worker=3   # more workers (useful only up to the partition count)
```


## Messaging (Kafka)

After an upload commits, the API publishes a `TaskQueuedEvent`
(`{event_id, task_id, file_id, attempt}`, key = `task_id`) to topic
`file-processing`. Workers form the consumer group `fileflow-workers`; each
partition is read by exactly one worker, so partitions cap parallelism.

The topic is created explicitly by `kafka-init` (auto-creation is off); the API
and workers refuse to start if it is missing, instead of waiting silently.

Delivery is **at-least-once**: auto-commit is off and a worker commits a
message's offset only after the task outcome is stored. Per message:
processed -> commit; invalid / task not `PENDING` -> skip (commit);
infrastructure error -> no commit, seek back, retry after a pause.

Known flaws, on purpose until later phases:
- **Dual write** (Phase 06): DB commit and Kafka publish are separate. With
  Kafka down the client gets 503 while the task is committed; the event is
  then lost or delivered late — the API cannot know
  (`experiments/phase05_kafka_down.sh`).
- **Stuck tasks** (Phase 10-11): a worker killed mid-task leaves it in
  `PROCESSING`; the redelivered event is rejected by the state machine
  (`experiments/phase05_kill_consumer.sh`).

Inspect Kafka:

```bash
K=/opt/kafka/bin
docker compose exec kafka $K/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic file-processing
docker compose exec kafka $K/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group fileflow-workers
docker compose exec kafka $K/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic file-processing --from-beginning --property print.key=true
```

## Task state machine

```text
PENDING ──> PROCESSING ──> COMPLETED
                      └──> FAILED
```

A file becomes `UPLOADED` and gets its `PENDING` task in one transaction.
Transitions are guarded UPDATEs (`WHERE status IN <allowed sources>`), so
concurrent claims cannot both win — see `experiments/phase03_claim_race.py`.
